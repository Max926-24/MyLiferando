# MyLiferando

Бэкенд сервиса доставки, по мотивам Lieferando. Заведения (рестораны, магазины, аптеки) создают заказы, диспетчер назначает на них курьеров, курьер забирает заказ и доставляет получателю.

Учебный проект на Spring Boot. Рассчитан на работу в России: клиенты идентифицируются по ИНН.

> **Статус:** в разработке. Готовы REST API, сервисы с правилами статусов, обработка ошибок, миграции базы, вход по логину и паролю, роли и разграничение доступа к своим и чужим данным, тесты сервисов.

## Стек

- Java 17
- Spring Boot 4 (Web MVC, Data JPA, Validation, Security)
- MapStruct (преобразование сущностей в DTO и обратно)
- PostgreSQL 16 в Docker
- Flyway (миграции базы)
- Maven (через `mvnw`, ставить Maven не нужно)

## Быстрый старт

Нужны **Java 17+** и **Docker**.

1. Клонировать репозиторий:
   ```bash
   git clone https://github.com/Max926-24/MyLiferando.git
   cd MyLiferando
   ```
2. Запустить базу данных:
   ```bash
   docker compose up -d
   ```
   PostgreSQL поднимется на порту **5433** (база `myliferando`, пользователь и пароль `postgres`).
3. Запустить приложение:
   ```bash
   ./mvnw spring-boot:run
   ```
   Приложение стартует на http://localhost:8080. Таблицы при первом запуске создаст Flyway по миграциям из `src/main/resources/db/migration`.
4. Запустить тесты (база должна быть запущена):
   ```bash
   ./mvnw test
   ```

Пересоздать базу с нуля (все данные удалятся):
```bash
docker compose down -v && docker compose up -d
```

## Вход и роли

Почти все запросы требуют входа. Используется **HTTP Basic**: логин и пароль передаются с каждым запросом (в Postman вкладка Authorization → Basic Auth). Пароли хранятся в базе только в виде хеша BCrypt.

| Роль | Кто это | Что может |
|---|---|---|
| `DISPATCHER` | диспетчер | заводит сотрудников, заведения и курьеров, назначает курьеров на заказы, оформляет и отменяет любые заказы, видит все заказы |
| `COURIER` | курьер | начинает и заканчивает свою смену, забирает и доставляет назначенные ему заказы, видит только их |
| `CLIENT` | заведение | оформляет и отменяет заказы своего заведения, видит только их |

### Откуда берутся пользователи

- **Первый диспетчер** создаётся миграцией `V5__add_first_dispatcher.sql`: логин `admin`, пароль указан в комментарии в этом файле. Это учебные данные для локальной базы; на настоящем сервере пароль нужно сменить.
- **С улицы** можно зарегистрироваться только как `CLIENT`: `POST /auth/register`. Роль в запросе не указывается, а присланная игнорируется.
- **Курьеров и диспетчеров** заводит диспетчер: `POST /users`.

### Пользователь и его карточка

Пользователь (`users`) — это только логин, пароль и роль. Заведение (`client`) и курьер (`courier`) — отдельные записи, к которым пользователь привязывается при создании: диспетчер указывает в запросе `username`. По этой связи система отличает свои данные от чужих.

Типичный порядок для нового курьера:

1. диспетчер создаёт пользователя с ролью `COURIER` — `POST /users`;
2. диспетчер создаёт курьера и указывает логин этого пользователя — `POST /couriers`;
3. курьер входит под своим логином и начинает смену.

Для заведения порядок такой же, только пользователь с ролью `CLIENT` может зарегистрироваться сам.

## API

### Пользователи

| Запрос | Кто может | Что делает |
|---|---|---|
| `POST /auth/register` | все, без входа | регистрация с ролью `CLIENT` |
| `POST /users` | `DISPATCHER` | создать пользователя с любой ролью |
| `GET /users/me` | любой вошедший | кто я: номер, логин, роль |

Пароль: от 10 до 30 символов.

### Заведения и курьеры

| Запрос | Кто может | Что делает |
|---|---|---|
| `POST /clients` | `DISPATCHER` | создать заведение и привязать к пользователю |
| `GET /clients` | любой вошедший | список заведений |
| `POST /couriers` | `DISPATCHER` | создать курьера и привязать к пользователю |
| `GET /couriers` | любой вошедший | список курьеров |
| `PATCH /couriers/{id}/start-shift` | `COURIER`, только сам | начать смену |
| `PATCH /couriers/{id}/end-shift` | `COURIER`, только сам | закончить смену |

### Заказы

| Запрос | Кто может | Что делает |
|---|---|---|
| `POST /orders` | `CLIENT` для своего заведения, `DISPATCHER` для любого | оформить заказ |
| `GET /orders` | любой вошедший | диспетчер видит все заказы, заведение свои, курьер назначенные ему |
| `PATCH /orders/{orderId}/assign/{courierId}` | `DISPATCHER` | назначить курьера |
| `PATCH /orders/{id}/pick-up` | `COURIER`, только назначенный | забрать заказ |
| `PATCH /orders/{id}/deliver` | `COURIER`, только назначенный | доставить заказ |
| `PATCH /orders/{id}/cancel` | `CLIENT` свой, `DISPATCHER` любой | отменить заказ |

### Коды ответов

| Код | Когда |
|---|---|
| `200`, `201` | успех; `201` при создании |
| `400` | запрос не прошёл проверку полей |
| `401` | не указаны или неверны логин и пароль |
| `403` | вход выполнен, но действие запрещено: не та роль или чужие данные |
| `404` | запись не найдена |
| `409` | конфликт: такая запись уже есть или действие невозможно в текущем статусе |

## Модель данных

```
Client (заведение) 1 ──── * Order (заказ) * ──── 0..1 Courier (курьер)
        │                                                  │
        └──── 0..1 User (пользователь) 0..1 ───────────────┘
```

### User — пользователь

| Поле | Описание |
|---|---|
| `username` | логин, уникальный |
| `password` | хеш пароля (BCrypt), в ответах API не отдаётся |
| `role` | `CLIENT`, `COURIER` или `DISPATCHER` |

### Client — заведение-отправитель

| Поле | Описание |
|---|---|
| `name` | название |
| `address` | адрес, откуда курьер забирает заказ |
| `email` | уникальный |
| `phone` | до 20 символов |
| `clientType` | чем занимается: ресторан, магазин, автосервис, аптека, алкомаркет, другое |
| `legalType` | кто по закону: юрлицо, ИП, физлицо |
| `inn` | ИНН, уникальный: 10 цифр у юрлица, 12 у ИП, у физлица необязателен |
| `user` | пользователь, который входит от имени заведения |

### Courier — курьер

| Поле | Описание |
|---|---|
| `name` | имя |
| `phone` | уникальный |
| `transport` | пешком, велосипед, машина |
| `status` | не на смене, свободен, везёт заказ |
| `user` | пользователь, под которым входит курьер |

### Order — заказ

| Поле | Описание |
|---|---|
| `client` | кто отправляет (обязательно) |
| `courier` | кто везёт (пусто, пока курьер не назначен) |
| `description` | что везём (необязательно) |
| `deliveryAddress` | куда везём |
| `recipientName`, `recipientPhone` | кому отдать |
| `status` | статус заказа |
| `createdAt`, `deliveredAt` | время создания и доставки, ставит система |

## Жизненный цикл заказа

```
CREATED ──► ASSIGNED ──► PICKED_UP ──► DELIVERED
   │            │            │
   └────────────┴────────────┴──► CANCELLED
```

| Действие | Заказ | Курьер |
|---|---|---|
| курьер начал смену | — | `OFF_DUTY` → `AVAILABLE` |
| курьер назначен на заказ | `CREATED` → `ASSIGNED` | `AVAILABLE` → `BUSY` |
| курьер забрал заказ | `ASSIGNED` → `PICKED_UP` | — |
| заказ доставлен | `PICKED_UP` → `DELIVERED` | `BUSY` → `AVAILABLE` |
| заказ отменён | любой, кроме `DELIVERED` → `CANCELLED` | `BUSY` → `AVAILABLE` |
| курьер закончил смену | — | `AVAILABLE` → `OFF_DUTY` |

Курьер везёт не больше одного заказа одновременно.

## Структура проекта

```
src/main/java/de/ait/myliferando/
├── config/          SecurityConfig: правила доступа и шифрование паролей
├── domain/          сущности JPA: Client, Courier, Order, User
│   └── enums/       ClientType, LegalType, CourierStatus, OrderStatus, Transport, Role
├── repository/      репозитории Spring Data JPA
├── dto/             объекты запросов и ответов API: client/, courier/, order/, user/
│   └── mapping/     мапперы MapStruct: ClientMapper, CourierMapper, OrderMapper, UserMapper
├── service/         бизнес-логика, правила смены статусов, проверки «своё или чужое»
│   └── interfaces/  интерфейсы сервисов
├── controller/      REST-контроллеры
└── exceptions/      свои исключения и общий обработчик ошибок

src/main/resources/
├── application.yml  настройки приложения
└── db/migration/    миграции Flyway, V1 ... V5
```

Схему базы меняют только новые файлы миграций. Уже применённую миграцию править нельзя.
